Overview#

The KVS component realizes the feature Persistency (feat__persistency). It stores key-value pairs of an application persistently in the file system, provides default values and keeps snapshots of the persisted data. The component is implemented in C++ and in Rust with the same API concept.

Description#

An application opens a KVS instance with a builder (KvsBuilder), which defines the instance ID, the snapshot to load and whether persisted data and default values are required. All key-value pairs of an instance are held in memory. Persisted data is loaded when the instance is opened and written only when the application calls flush. Each data file is stored together with an Adler-32 hash file, which is checked when the data is loaded. Before a flush the existing files are kept as snapshots.

Design decisions:

  • The data is stored in JSON format in the file system (Persistent Data Storage Format (comp_req__kvs__pers_data_store_fmt), Persistent Data Storage Bac... (comp_req__kvs__pers_data_store_bnd)).

  • C++: the file system, JSON parser and writer and logger are used via the interfaces of the S-CORE baselibs (logic_arc_int__baselibs__filesystem, logic_arc_int__baselibs__json, logic_arc_int__log_cpp__logging).

  • Rust: the storage is accessed via the KvsBackend trait, the default backend JsonBackend uses the Rust standard library file API and the crates tinyjson and adler32.

Design constraints:

  • The API is synchronous. Asynchronous flush (Async API (comp_req__kvs__async_api)) and change callbacks (Callback Support (comp_req__kvs__callback_support)) are not realized.

  • Snapshots are created only by flush. Explicit snapshot creation, removal and slot query (Snapshot Create API (comp_req__kvs__snapshot_create_api), Snapshot Remove API (comp_req__kvs__snapshot_remove_api), Snapshot Slot Free Query API (comp_req__kvs__snapshot_slot_free_api)) are not realized.

  • The component does not prevent that an instance is opened by more than one process (Single Process Access (comp_req__kvs__single_process_access) is not realized).

Rationale Behind Architecture Decomposition#

The component is not split into internal components. It provides one functionality (persistent key-value storage) with a small set of interfaces, and its parts are only used together. The C++ and the Rust implementation are language bindings of the same component (Language Bindings (comp_req__kvs__language_bindings)). The decomposition into units is described in the detailed design (KVS Detailed Design (doc__kvs_detailed_design)).

Dynamic Architecture#

KVS is the only component of the feature. The interactions of the component with its user and with the used interfaces are described in the dynamic views of the feature architecture (Persistency KVS Feature Arc... (doc__persistency_kvs_architecture)), therefore no additional dynamic view is created on component level.

Interfaces#

The component provides the following public interfaces for C++ and Rust. They realize the logical interface IKvs (logic_arc_int__persistency__interface), which is implemented by persistency::kvs (comp__persistency_kvs). The realized IKvs operation is named in the description of each interface operation. The implements link from the interface operations to the logical interface operations is added as soon as the operations of IKvs are defined as logic_arc_int_op in the platform documentation.

The interface documentation (parameters, return values, error codes) is part of the source code.
